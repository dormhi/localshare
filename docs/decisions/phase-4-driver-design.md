# Phase 4 driver proof — design preparation

Status: preparation started, 2026-09-30. This is a working design, not an accepted driver implementation or a validation report.

## Scope and confirmed boundaries

The owner authorized starting Phase 4 while combining outstanding Phase 3 tests with the next Windows test session. Windows 11 x64 and ARM64 remain the targets. The approved architecture is a separate C++ UMDF indirect display driver using supported IddCx APIs. The WinUI host and Android control endpoint retain their current roles. Exactly one virtual monitor is permitted. Video encoding, desktop streaming, touch and release packaging remain outside Phase 4.

The driver reports an adapter, monitor and approved display modes; IddCx supplies desktop images through a Direct3D swap chain. These baseline facts are summarized in the existing [driver notes](../../src/windows/driver/README.md), with their primary reference and checked date. Exact callbacks, supported interface versions, WDK project metadata and signing inputs must be selected and verified in the Windows environment before implementation.

## Lifecycle to implement and validate

| State / event | Required result |
| --- | --- |
| Driver/adapter initialization | Report capabilities actually supported by the selected Windows/adapter path; surface failure without adding a phantom monitor |
| Proof activation | Advertise exactly one monitor and only the approved proof modes |
| Swap-chain assignment/reassignment | Own processing resources explicitly; release previous resources before replacing them |
| Stop/removal or initialization failure | Stop work, release swap-chain resources and remove the proof monitor without disturbing physical displays |
| Restart/reboot | Recover deterministically without duplicate or orphan monitors |

Adapter/GPU differences, scaling and display arrangement require Windows evidence. No mock or source-contract check can establish these behaviors. Driver processing must keep memory/work bounded and handle shutdown and failure paths; concrete limits and synchronization follow the supported WDK implementation.

## Decisions and dependencies

- **Proof modes (approved 2026-09-30):** 1280×800 at 60 Hz and 1920×1080 at 60 Hz. These are virtual Windows display modes. Windows/adapter validation is pending; they do not claim either tablet panel supports or runs at these settings.
- **Windows test target and recovery:** deferred until the owner has a Windows environment. Recommend an isolated compatible test PC/VM; document limitations if virtualized.
- **Signing/install route:** deferred until the actual toolchain/target is known. Development test signing is accepted in principle, but no installation or machine configuration action is authorized yet.
- **USB/monitor lifecycle boundary:** before implementing the host-to-driver control path, document how explicit stop and cable loss remove the monitor through supported interfaces. The Phase 4 acceptance text includes unplug cleanup; do not silently reduce it to standalone manual removal or pull in Phase 6 streaming. Present any material architecture choice to the owner with concrete supported options after investigating the Windows template.

## Implementation sequence and commit gates

1. Complete offline scope and combined validation notes.
2. On Windows, identify supported toolchain/template, finalize pending decisions and create the genuine WDK project.
3. Implement small units: adapter/monitor enumeration, approved modes, swap-chain resource lifecycle, and proof install/remove/recovery instructions.
4. Run relevant Windows build/static analysis/runtime checks before each driver behavior commit; keep private signing material outside Git.
5. Close Phase 3 and Phase 4 independently using the [combined checklist](../testing/phase-3-4-windows-checklist.md).

Documentation-only preparation can be checked on macOS with the existing offline validator, source-contract suite, link review and `git diff --check`. This does not extend Phase 1's static-only exception to driver implementation. No `.vcxproj`, INF, binary or signing/install automation has been generated by this preparation.
